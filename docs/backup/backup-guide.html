Backup & recovery

Backup guide

Create a complete backup of PostgreSQL and uploaded files. A backup is only finished when both parts succeed and checksums are written.

What a complete backup includes

  • PostgreSQL — logical custom-format dump of the whole database.
  • Uploads — the Compose uploads volume (/data), including attachments and installed plugins stored there.
  • Manifest + checksums — version metadata and SHA-256 hashes for every artifact.

The backup does not include .env, CREDENTIALS_KEY, or Docker Compose files. Keep those separately. If you use MinIO / S3 (DOCKER_S3_ENDPOINT or the s3 profile), back up that object store with your own tooling — it is outside the standard Rolodex backup format.

While the backup runs, the script stops the rolodex service briefly so the database dump and uploads archive stay consistent, then starts it again.

Create a backup

In the app, an owner can open Admin → Backups, create a complete backup, download or restore it, upload an archive, and configure automatic backups with retention. In-app backups are stored on the host path set by BACKUP_DIR (default ./backups, mounted at /backups in Docker) and use the same artifact format as the host scripts.

From the host (Linux, macOS, WSL, or Git Bash), in the directory that contains docker-compose.yml:

./scripts/backup.sh

Optional destination directory:

./scripts/backup.sh /mnt/nas/rolodex-backups/2026-11-20_093000

Default layout:

backups/
└── 2026-11-20_093000/
    ├── database.dump
    ├── uploads.tar.gz
    ├── manifest.json
    └── checksums.sha256

Artifacts are written to a .partial directory first. Only after both components and checksums succeed is the folder renamed to the final stamp. A failed run does not leave a directory that looks complete.

Prefer copying finished backups to another disk or machine. A backup on the same disk as the live install does not protect against disk failure.

Inspect the backup

ls -la backups/2026-11-20_093000
cat backups/2026-11-20_093000/manifest.json
cat backups/2026-11-20_093000/checksums.sha256

manifest.json records the application version, PostgreSQL version, creation time, and component filenames. Use it when restoring on another host.

Verify without touching production

./scripts/verify-backup.sh backups/2026-11-20_093000

Verification checks checksums, the manifest, the uploads archive listing, and restores the dump into a disposable Postgres container. The live Rolodex containers stay running. Successful verification is not the same as a production restore — see the restore guide.

Preserve CREDENTIALS_KEY

Integration credentials in the database are encrypted with CREDENTIALS_KEY from .env. Restoring the database without that exact key leaves encrypted values present but unusable. Store the key in a password manager or sealed note — never only inside the backup folder, and never commit it to git.

Keep multiple generations

Prefer several stamped directories on independent storage (another disk, NAS, or restic/CronMaster). In the app, Admin → Backups can run on a cron schedule and prune older in-app backups after each successful run according to the retention setting. Host-script folders under BACKUP_DIR are not pruned by that setting unless they share the same directory. Always run verify-backup.sh on a copy before you rely on it.

Windows notes

Prefer Admin → Backups in the browser for routine create, download, upload, and restore. For host scripts, use WSL or Git Bash in the repo (or compose) directory. From PowerShell you can call them through bash: 

bash ./scripts/backup.sh
bash ./scripts/verify-backup.sh backups/2026-11-20_093000

A download from Settings → Backup is database-only. It is not a complete backup. Use Admin → Backups or scripts/backup.sh for recovery.
